# ADR 0011: M4 minimal messaging protocol and delivery contract

- Status: Accepted for M4
- Date: 2026-09-14
- Scope: M4 protocol/authentication/delivery semantics and bounded mailbox custody

## Context

M3 provides authenticated, ratcheted 1:1 ciphertext and durable session advancement, but deliberately does not route ordinary messages. M4 must add WSS routing, direct online delivery, a bounded offline mailbox, acknowledgement/retry semantics and local conversation history without making the server a plaintext or identity-trust authority.

The existing `kenato.v1.Envelope` is retained as the minimum server-visible encrypted unit. M4 extends it only with the authenticated sender routing id; user-visible type/content remain encrypted.

## Decision

### Identity-authenticated WSS

A routing identifier is not authentication. Every new WSS connection starts unauthenticated.

1. The server generates 32 random bytes and an expiry no more than 30 seconds in the future and sends `MessagingAuthChallenge`.
2. The challenge is bound to that connection, single-use, and discarded after the first auth attempt, successful or not.
3. The client signs the exact canonical payload below using its existing long-lived Kenato P-256 identity key and sends `MessagingAuthResponse`.
4. The server resolves the submitted identity id internally, verifies that the public key hashes to that id, verifies the ECDSA/SHA-256 signature, and authenticates the connection only on exact challenge/expiry match.
5. Unknown identity, malformed proof, wrong signature and replay all fail through the same non-enumerating authentication result.

Canonical bytes:

```text
"KENATO-MESSAGING-AUTH-V1\0"
|| identity_id[32]
|| challenge[32]
|| expires_at_unix_seconds:u64be
```

Only one authenticated WSS connection is active for one identity in M4. After a new connection authenticates successfully it atomically replaces the older connection. Multi-device fan-out is not part of M4.

TLS/WSS endpoint authentication remains required at the reviewed reverse-proxy deployment boundary. The P-256 challenge proves Kenato identity ownership; it is not a substitute for TLS.

### Envelope and encrypted plaintext

`Envelope` remains server-visible routing metadata plus opaque ciphertext:

- protocol version = 1;
- sender identity id = exactly 32 bytes and must equal authenticated connection identity on send;
- recipient identity id = exactly 32 bytes and distinct from sender;
- message id = exactly 16 non-zero random bytes generated by the sender;
- ciphertext = encoded M3 `SessionCiphertext`, opaque to the server, maximum 64 KiB in M4;
- expiry = future Unix seconds, no more than 72 hours from server acceptance;
- full encoded envelope = maximum 96 KiB.

A WSS frame is at most 100 KiB. M4 text is at most 16 KiB UTF-8.

Before M3 encryption the sender encodes `MessagingPlaintext` containing the same sender id, recipient id, message id and expiry, plus authenticated `sent_at` and text. After M3 authentication/decryption the recipient must compare those protected values to the outer `Envelope` and to the M3 session/ciphertext identities. Any mismatch fails closed before application-visible delivery or ACK. This prevents a malicious relay from renaming a message, changing its peer binding, or extending its authenticated expiry while leaving ciphertext intact.

M4 text-only semantics are intentionally inside ciphertext. No plaintext message-type discriminator is added to server-visible metadata.

### Expiry

A message is expired exactly when `now >= expires_at`. The server accepts an envelope only when `expires_at > now` and `expires_at - now <= 72h`. The encrypted plaintext also requires `expires_at > sent_at` and a maximum 72-hour span. The server does not rewrite the sender's expiry.

An honest server deletes expired mailbox rows during bounded cleanup. A malicious server may retain metadata outside policy, but cannot alter the authenticated inner expiry without recipient detection.

### Direct delivery and mailbox custody

The preferred online path performs no durable mailbox write.

- If the recipient has an authenticated writable connection, the server attempts direct delivery.
- Direct delivery becomes terminal for the sender only after the authenticated recipient ACKs the message.
- If direct delivery cannot complete or becomes backpressured/disconnected, the server may fall back to the bounded durable mailbox. `SendAccepted` is emitted after that durable commit.
- If the recipient is unavailable from the start, the server stores the bounded opaque envelope first and then emits the same `SendAccepted`.
- `SendAccepted` intentionally contains no online/offline/delivery-mode bit.

The two terminal meanings are therefore: recipient acknowledged direct delivery, or server accepted durable mailbox custody. A lost `SendAccepted` may cause an exact sender retry; M4 is at-least-once at the transport boundary and recipient deduplication is mandatory.

Timing may still reveal coarse delivery latency to an already established contact. M4 does not claim traffic-analysis or presence-hiding guarantees.

### Duplicate and conflict semantics

The sender/message-id pair is unique for M4. A durable mailbox row is additionally bound to its recipient and exact envelope bytes.

- an exact retry of the same retained envelope is idempotent;
- reuse of the same sender/message id with a different recipient, ciphertext or expiry is a conflict and is rejected generically;
- direct-only delivery does not require an unbounded replay cache, so a sender retry after a lost response may be redelivered;
- recipients deduplicate by authenticated sender/message id after validating the encrypted context and still ACK an already durably delivered duplicate;
- reordering is permitted; M3 remains responsible for authenticated ratchet/out-of-order cryptographic handling within its fixed engine bounds.

### ACK and deletion

`MessagingDeliveryAck` carries sender identity id and message id. The recipient identity comes only from authenticated WSS connection state.

The server may delete a retained mailbox row only when all three values match: authenticated recipient, stored sender, message id. Exact duplicate ACK is harmless. ACK for another recipient/sender/message must not delete data or reveal target existence.

A recipient sends ACK only after:

1. M3 authentication/decryption succeeds;
2. outer Envelope, M3 peer identities and encrypted M4 plaintext context agree;
3. the advanced ratchet state and a crash-safe durable local delivery handoff are committed;
4. that handoff is idempotently reflected in local conversation history.

M3's existing rule that plaintext is not application-visible before durable ratchet advancement remains unchanged. Because a crash after ratchet commit but before history persistence could otherwise make the retransmitted ciphertext an undecryptable replay, #53 must introduce a bounded durable delivery handoff/journal coordinated with the ratchet commit (or an equivalent crash-safe construction) before enabling ACK. Application code must never ACK merely because a plaintext value existed transiently in memory.

### Mailbox persistence and limits

The #51 mailbox is a separate SQLite database from the M2/M3 contact/bootstrap database. This keeps message-retention/ACK deletion independent from destructive invite/session-bootstrap lifecycle operations while preserving the same local file hardening: regular file, mode `0600`, WAL, synchronous `FULL`, STRICT schema and fail-closed schema versioning.

Recipient existence is checked through an internal identity-directory interface backed by the contact store; no public identity lookup is introduced. The mailbox database itself contains no public identity bundles or contact state.

The durable mailbox enforces:

- maximum 500 retained messages and 16 MiB of encoded envelopes per recipient;
- maximum 1,000 retained messages and 32 MiB per sender across recipients;
- maximum 100,000 retained messages and 256 MiB globally;
- maximum 72-hour retention;
- maximum 96 KiB encoded envelope and 64 KiB ciphertext;
- delivery pages of at most 50 retained messages;
- physical expiry cleanup batches of at most 1,000 rows;
- transactional quota/idempotency checks plus a SQLite `BEFORE INSERT` capacity trigger as a storage-level backstop;
- indexes for recipient delivery, sender accounting and expiry cleanup.

The physical global quotas count rows awaiting expiry cleanup, so delayed maintenance cannot allow unbounded disk growth. Expired rows are excluded from delivery immediately at the exact expiry boundary even before physical deletion.

Only opaque encrypted envelopes and minimum routing/timing metadata are retained. User plaintext, contact names, session keys and message semantic type are never mailbox columns or logs.

### Error/privacy behavior

Protocol errors are deliberately coarse (`MALFORMED`, `AUTHENTICATION_FAILED`, `SEND_REJECTED`, `RETRY_LATER`). Public behavior must not distinguish unknown recipient, offline recipient, quota details or internal mailbox state in a way that creates a user-enumeration endpoint.

## Consequences

- M4 adds a second proof of possession for the existing identity key, but does not create a new trust anchor.
- The server learns sender, recipient, timing, ciphertext size and bounded mailbox state. It does not learn message plaintext or semantic type.
- Direct delivery minimizes durable metadata while mailbox fallback provides bounded offline delivery.
- At-least-once transport requires authenticated application-level deduplication and careful local crash ordering.
- The separate mailbox database adds one additional local durable file set but isolates message-retention failure and migration policy from M2/M3 relationship/bootstrap state.
- The protocol is intentionally single-device/single-active-connection for M4; multi-device semantics require a future reviewed design.
- M5 calling/WebRTC behavior is unaffected and remains out of scope.
